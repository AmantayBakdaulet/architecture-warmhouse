### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удаленно включать и выключать отопление в своем доме через веб-интерфейс
- Система поддерживает только один вид оборудования: модуль управления отоплением с датчиком температуры. Сейчас подключено 100 модулей, веб-клиентов тоже 100
- Команды идут только от сервера к устройству, само устройство в систему ничего не отправляет
- Подключить датчик самому нельзя. Приезжает специалист, ставит оборудование и заводит его в системе (в коде это `POST /api/v1/sensors`)
- Состояние устройства хранится в поле `status`, меняется через `PUT /api/v1/sensors/:id` или `PATCH /api/v1/sensors/:id/value`

**Мониторинг температуры:**

- Пользователи могут посмотреть текущую температуру: по всем датчикам, по одному датчику или по комнате (`GET /api/v1/sensors/temperature/:location`)
- Система поддерживает один тип датчика, `temperature`. У датчика есть название, комната, единица измерения и статус
- Температура запрашивается у датчика в тот момент, когда пользователь открывает список. Датчик сам данные не присылает
- История не хранится, в базе лежит только последнее значение.


### 2. Анализ архитектуры монолитного приложения

- Язык: Go, фреймворк Gin
- База данных: PostgreSQL 16, одна таблица `sensors`
- Архитектура: монолит. Внутри есть разделение на пакеты `handlers`, `services`, `db`, `models`, но собирается и запускается все одним приложением
- API: REST, JSON, все методы под `/api/v1`, плюс `/health`
- Взаимодействие: синхронное. Запрос пользователя -> чтение из БД -> HTTP-запрос к датчику -> ответ
- Данные с датчиков: сервер сам ходит к датчику по HTTP (адрес в переменной `TEMPERATURE_API_URL`, тайм-аут 10 секунд)
- Масштабируемость: только все приложение целиком, отдельные части масштабировать нельзя
- Развертывание: docker-compose, один контейнер с приложением и один с базой. Чтобы обновиться, нужно остановить все приложение

### 3. Определение доменов и границы контекстов

Выделил бы такие домены:

| Домен | Тип | Контексты |
| --- | --- | --- |
| Управление устройствами | основной | Реестр устройств, управление отоплением |
| Телеметрия | основной | Мониторинг температуры |
| Сценарии | основной | Настройка сценариев и расписаний |
| Подключение устройств | поддерживающий | Регистрация и настройка устройства |

Границы контекстов:

- Реестр устройств знает, какие устройства есть и где они стоят. Как именно управлять устройством, он не знает
- Управление отоплением отвечает за команды включить/выключить и текущее состояние. Для света, ворот и камер в новой системе будут свои контексты, чтобы они не зависели друг от друга
- Мониторинг температуры работает с показаниями. Нагрузка здесь зависит от количества датчиков, а не пользователей

### **4. Проблемы монолитного решения**

Пока домов 100, монолит справляется. Проблемы начнутся при росте и новых требованиях:

- Масштабировать можно только все приложение сразу, хотя опрос датчиков и запросы пользователей растут по-разному
- Все синхронно. Запрос пользователя ждет ответа от датчиков, датчики опрашиваются по очереди. На тысячах устройств это работать не будет
- Связь только от сервера к устройству. Устройство не может само сообщить о событии (например, что ворота открыты), а серверу нужен доступ в домашнюю сеть пользователя
- Пользователь не может подключить устройство сам, нужен выезд специалиста. Для SaaS с самообслуживанием это не подходит
- Тип устройства зашит в код и в таблицу. Чтобы добавить свет, ворота или камеру, придется менять и модель, и схему базы
- Нет пользователей, домов и авторизации, данные разных клиентов никак не разделены
- Не хранится история показаний, поэтому нельзя показать телеметрию и сделать сценарии
- Любое обновление останавливает все приложение. Ошибка в одной части роняет все. Приложение и база в одном экземпляре
- Вся команда работает в одной кодовой базе и выпускается одним релизом

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
